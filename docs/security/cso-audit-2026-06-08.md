## P1 — Embarrassing if Found in Week 1 of Public

### P1-1. Next.js 16.2.4 has known Middleware-bypass CVE (GHSA-26hh-7cqf-hhc6)

**File:** `package.json:36` — `"next": "16.2.4"`
**Confidence:** 9/10 (advisory text matches the middleware-segment-prefetch
attack class; not actively verified against zBase's specific routes)
**Category:** A03 Software Supply Chain Failures + A05 Injection (privacy)

`npm audit` reports Next.js 16.2.4 is in the vulnerable range for three
high-severity advisories:
- GHSA-26hh-7cqf-hhc6 — **Middleware/Proxy bypass via segment-prefetch routes**
- GHSA-3g8h-86w9-wvmq — Middleware redirect cache poisoning
- GHSA-8h8q-6873-q5fj — Server Components DoS

The Middleware-bypass is load-bearing for zBase: `src/middleware.ts` is the
single mechanism that strips `x-forwarded-for`, `x-real-ip`,
`cf-connecting-ip`, `user-agent`, `accept-language`, `referer`, `cookie`
from `/api/facilitator/*`, `/api/withdraw`, `/api/asp-update`,
`/api/x402-pay`. If the middleware is bypassable, **the privacy claim
documented in `docs/gitbook/trust-model.md` is violated** — the route
handler will see the original IP and identify the buyer.

**Exploit sketch:**
```
attacker crafts /api/facilitator/settle prefetch URL (per GHSA-26hh-7cqf-hhc6 PoC)
→ middleware skipped → route handler reads x-forwarded-for
→ Vercel server logs now contain {buyer IP, nullifier, recipient, amount}
→ stored in Vercel Log Drains / observability vendor
→ subpoena / breach → buyer-to-payment linkage recovered post-hoc
```

**Remediation:**
1. `npm install next@16.2.7` (non-breaking, per `npm audit`'s
   `fixAvailable.isSemVerMajor: false`).
2. Re-run `npm audit` to confirm clean for direct Next.
3. Add an integration test that calls a known segment-prefetch payload
   against `/api/facilitator/settle` and asserts the route never sees
   `x-forwarded-for`.

### P1-2. `/api/withdraw` logs deposit metadata to console (correlation surface)

**File:** `src/app/api/withdraw/route.ts:141-145, 244, 369-370, 483, 525-531`
**Confidence:** 10/10 (read code)
**Category:** A09 Logging Failures (sensitive data in logs) / Information Disclosure (STRIDE-I)

The middleware strips identifying request headers (good), but the route
handler then `console.log`s the full per-payment fingerprint:
- `value` (deposit denomination, in atomic USDC)
- `label` (on-chain Merkle leaf identifier — unique per deposit)
- `commitment` (Poseidon hash that's on-chain at a specific tx index)
- `recipient` (the destination wallet)
- `txHash` of the relay (links commitment ↔ destination on-chain)

These flow to Vercel's log aggregation. Anyone with Vercel project access
(team members, Vercel staff under legal process, log drain subscribers,
breach attackers) can reconstruct every settle: who paid (via the
commitment → on-chain Deposited event → depositor address), and who
received (via `recipient`). **This defeats the unlinkable-settle property
the product sells.**

On revert, `pubSignals` + `State root used` + `Commitment` + `Label` are
also emitted — same correlation hazard plus debug minutiae that don't
need to be in production logs.

**Exploit sketch:**
```
- adversary gains read access to Vercel logs (insider, breach, subpoena)
- greps for "[Withdraw] recipient" → list of (timestamp, recipient, commitment)
- for each commitment, scans Base Sepolia for the Deposited tx with same hash
- → maps every on-chain deposit to its eventual recipient
- → entire privacy guarantee is broken retroactively for all past settles
```

**Remediation:**
1. Replace these console.log calls with a structured logger that obeys
   `LOG_LEVEL` and elides anything tagged "privacy-sensitive" in prod.
2. Specifically remove `value`, `label`, `commitment`, `recipient`,
   `pubSignals`, `State root used`, `ASP root used` from prod logs.
3. Keep only counters + status (e.g. `[Withdraw] success duration=12345ms`)
   — anything that doesn't correlate buyer to recipient.
4. Also redact `[Agent Registry] tx #...` line in `settle/route.ts:315`
   (logs agent name + total spent → identity leak for any registered agent).
5. Add a "logs scrubber" test: tail logs from a known settle and grep for
   `commitment`/`recipient` — must return zero.

### P1-3. Deployed pool source not vendored — FIND-301 mitigation un-verifiable locally

**Files:** `contracts/PrivacyPoolMorpho.sol` (patch only), no upstream
`PrivacyPool.sol` / `Entrypoint.sol` in repo
**Confidence:** 7/10 (verified the patch file is not the deployed contract
ABI; assumed deployed pool follows 0xbow's documented ABI)
**Category:** A08 Software or Data Integrity Failures

PR #26 closes FIND-301 by server-resolving `feeRecipient` + `relayFeeBPS`
from the nullifier's Upstash tier and ignoring caller body fields. But the
on-chain enforcement of that fee split depends on the deployed pool at
`0x4ebcfeaf...` actually decoding the relay tuple as
`(recipient, feeRecipient, relayFeeBPS)` and honoring `relayFeeBPS` to
route a share to `feeRecipient`. **There is no copy of the deployed pool's
Solidity source in this repo to confirm that.** Only the
yield-distribution patch (`contracts/PrivacyPoolMorpho.sol`) is in the
codebase, and that file does not contain any `feeRecipient` /
`relayFeeBPS` enforcement logic.

If the deployed 0xbow pool doesn't actually enforce the bps split — or
enforces a different field shape — the FIND-301 fix is cosmetic:
`/api/withdraw` builds the relay struct, on-chain ignores the fee fields,
and the recipient gets 100% of the amount with treasury getting 0%.

**Exploit sketch:**
```
- send buyer through full flow on Base Sepolia after PR #26
- read the WithdrawalRelayed event from the on-chain receipt
- if _feeAmount == 0 and treasury balance unchanged: FIND-301 not actually closed
- attacker burns access fee once → gets 100% settles forever
```

**Remediation:**
1. Vendor the deployed pool's Solidity source into this repo at
   `zbase-protocol/pkg/contracts/src/contracts/PrivacyPool.sol` and
   `…/Entrypoint.sol` — even read-only — so future audits can verify the
   relay ABI matches.
2. Add an integration test under `npm run test:e2e` that exercises a
   $0.667 settle (the standard-tier minimum) and asserts the on-chain
   `_feeAmount` ≥ floor and treasury balance increased.
3. Add a forge test against the vendored pool with a mock relay data and
   assert the right split occurs.

### P1-4. Rate-limiter mem-fallback collapses to per-Lambda buckets in production

**File:** `src/lib/rate-limit.ts:32-36, 73-102`
**Confidence:** 9/10 (read code + Vercel cold-start semantics)
**Category:** A06 Insecure Design (rate limiting)

If `UPSTASH_REDIS_REST_URL` / `UPSTASH_REDIS_REST_TOKEN` (or KV_REST_API_*
aliases) are absent in production env, `USE_UPSTASH` is `false` and the
limiter degrades to `memBuckets: Map<...>` — **per-process state**. On
Vercel, every Lambda cold start gets a fresh empty map. Under load Vercel
spins up N concurrent containers, and a single IP attacker hits 10×N
authorizes/min instead of 10/min, each one firing
`getTransactionReceipt` to Base Sepolia.

The PR #20 commit message says "Upstash provides shared rate limiting"
but provides no startup-time assertion that Upstash is actually
configured. If a future deploy forgets to set the env vars, the limiter
silently degrades with no alert.

**Exploit sketch:**
```
- attacker hits POST /api/facilitator/authorize from a single IP
- bursts to 100 req/s; Vercel scales to 10 containers, each owning own bucket
- 100 RPC calls/s to Base Sepolia → burns the Alchemy/Infura quota in minutes
- legitimate users get 429s from upstream RPC → service down
```

**Remediation:**
1. Add a `assertUpstashOrLog()` startup hook that warns/blocks in
   production if `USE_UPSTASH === false`. Vercel build env can gate this.
2. Surface `rl.backend === "memory"` to ops dashboards (Sentry alert,
   PagerDuty page).
3. Document in `.env.local.example` that Upstash is REQUIRED before
   flipping `ZBASE_FEE_REQUIRED=true` in mainnet (the current text says
   "recommended").

### P1-5. `/api/providers/register` writes to disk — broken/silent on Vercel

**File:** `src/app/api/providers/register/route.ts:33, 77-84`
**Confidence:** 8/10 (Vercel serverless FS is ephemeral; writes to /tmp
don't survive cold start and writes outside /tmp throw EROFS)
**Category:** A06 Insecure Design / A10 Mishandling of Exceptional Conditions

`saveRegistry()` does `fs.writeFile(REGISTRY_PATH, ...)` where
`REGISTRY_PATH = process.cwd() + "data/providers.json"`. On Vercel the
function filesystem is read-only outside `/tmp`. The write throws EROFS,
falls into the catch in the POST handler, returns "Unknown error" with
status 500, **and silently loses the registration**. Concurrent reads
load the empty registry — provider stealth derivation always misses.

Even worse: if the cwd is read-only and the in-process `cache` is
already populated, the in-process state will diverge from any other
Lambda container's, producing nondeterministic "provider not found" /
"duplicate metaAddress" responses depending on which Lambda the user
lands on.

**Exploit sketch:**
```
- registered provider on Lambda A → cache populated, disk write fails
- next call lands on Lambda B → cache empty, no disk file → provider missing
- /api/facilitator/settle sees no provider for the payTo → no stealth address
  → payment lands on the literal payTo (privacy regression silently happens)
```

**Remediation:**
1. Move providers registry to Upstash (same as authorization storage):
   `zbase:provider:<id>` and `zbase:provider:bypayto:<lower>` keys.
2. Add an integration test that calls POST then GET from "different
   processes" (parallel invocations) and asserts the provider is
   returned.
3. Add auth (a Bearer token or signed admin nonce) to the POST handler
   — today it's open to anyone, so a malicious caller can register their
   meta-address as the fallback for a high-traffic provider's payTo and
   intercept funds.

### P2-1. ASP postman single-key still in production

**File:** `src/app/api/asp-update/route.ts:148-153`, `CLAUDE.md`
governance section
**Confidence:** 10/10 (known + documented in repo)
**Category:** STRIDE-E (Elevation of Privilege)

The single key at `0xcDB...843` can push arbitrary ASP roots. The
ThresholdEntrypoint scaffold exists at
`zbase-protocol/pkg/contracts/src/contracts/ThresholdEntrypoint.sol`
but is not deployed and not wired. Until 3-of-5 quorum is live, a
compromised POSTMAN key = ability to censor approvals OR push bad-actor
labels into the ASP. Documented as accepted risk in `docs/governance.md`
but worth re-noting in the audit context — this is the highest-impact
single point of failure in the system.

**Remediation:** Continue the threshold-signer recruitment + ceremony
documented in `docs/ceremony/` (currently gitignored, sensitive). Until
deployed, set up a Vercel hook that alerts on every `updateRoot` tx so a
rogue ASP push triggers an out-of-band review window. **Migrate
POSTMAN_PRIVATE_KEY to a hardware-backed signer (Ledger / AWS KMS
asymmetric key) immediately** — currently it's a raw hex string in
Vercel env vars.

### P2-2. Agent registry is in-process Map — silent spend-limit bypass on cold start

**File:** `src/app/api/agent/register/route.ts:44`
**Confidence:** 9/10
**Category:** A06 Insecure Design, A09 Logging

`const agentRegistry = new Map<string, AgentRecord>();` lives in
module-global state. Every Lambda cold start = fresh empty registry.
The agent's spend counter (`dailySpent`, `totalSpent`) resets to zero
whenever the container restarts. **A registered agent's `maxSpendPerDay`
is effectively ignored** — they can hit the daily limit, wait for cold
start (a few minutes idle), and spend again.

Also: registering the same agent on Lambda A doesn't show it on Lambda
B. The /verify and /settle handlers will return "Agent not found" for
the same agentId 50% of the time, depending on routing.

**Remediation:** Move registry to Upstash. Optionally make it on-chain
(the README suggests "on-chain registry" but the code is in-memory).

### P2-3. Interest route stores PII (UA, email) in `globalThis` indefinitely

**File:** `src/app/api/interest/route.ts:15-17, 129`
**Confidence:** 8/10
**Category:** A02 Security Misconfiguration / PII handling

`const memory: Entry[] = (globalThis...).__zbaseInterest ?? []` accumulates
all email signups + truncated UA strings in process memory forever. No
TTL, no eviction. On Vercel this also doesn't persist (so the data is
unreliable for marketing AND a privacy hazard if memory snapshots ever
leak). Email is forwarded to Resend, which is fine, but the in-process
copy is unnecessary.

**Remediation:** Drop the in-memory `memory` array. Persist only via the
external webhook + Resend email. If a count is needed, store it in Upstash.

### P2-4. No rate-limit on `/api/asp-update` (POSTMAN gas burn)

**File:** `src/app/api/asp-update/route.ts:45`
**Confidence:** 9/10
**Category:** A06 Insecure Design

`POST /api/asp-update` triggers a real on-chain `updateRoot()` tx signed
by POSTMAN_PRIVATE_KEY. An attacker hitting this endpoint in a loop
can burn the postman's ETH balance via repeated gas spend (no-op if root
unchanged is checked, but the eth_call + getLogs sweep still costs).

This route is covered by the middleware (privacy header strip) but NOT
by the rate-limit middleware. Anyone can hit it.

**Remediation:** Add `checkRateLimit(request, "asp-update", undefined)`
with a low cap (e.g. 6/min) bound to IP (since middleware doesn't strip
IP from /api/asp-update — let me verify… actually it DOES; the matcher
includes /api/asp-update at middleware.ts:93). Therefore use the route
itself as the bucket key or accept a fully-global bucket here.
Alternative: gate this route behind a shared-secret header that the
internal `/api/demo/run` and frontend deposit flow set.

### P2-5. No rate-limit on `/api/agent/register` or `/api/providers/register`

**File:** as named
**Confidence:** 8/10
**Category:** A06 Insecure Design

Both endpoints write to in-process state (agent) or attempt disk writes
(providers). An attacker can flood them with junk to grow the in-process
Map (memory exhaustion on the Lambda) or fill Upstash if the providers
fix moves it there.

**Remediation:** Same `checkRateLimit` wrapper, conservative limits
(e.g. 5/min/IP).

### P2-7. `@noble/curves` duplicated in `packages/core/package.json`

**File:** `packages/core/package.json:22, 25`
**Confidence:** 10/10
**Category:** A02 Security Misconfiguration

Lines 22 and 25 both list `@noble/curves` — `^1.9.0` and `^1.6.0`. JSON
parsers tolerate duplicate keys but the resolution behavior depends on
the parser (npm picks the last). This is also a tell that future bumps
will miss one of the two pins and silently downgrade.

**Remediation:** Remove line 25. Pin exactly: `"@noble/curves": "1.9.0"`
(no caret, see P3-1).

### P2-8. `data/providers.json` would contain contact emails if committed

**Files:** `src/app/api/providers/register/route.ts:35-48`,
`.gitignore:111` (`data/providers.json` is gitignored)
**Confidence:** 9/10
**Category:** PII / A09

The file is gitignored today (`.gitignore:111`). If a future contributor
runs the dev server locally, registers a provider, then accidentally
adds the file (e.g. `git add data/` instead of `git add data/seed-notes`),
contact emails would land in git history. The schema also stores email,
which means even on the Upstash migration recommended in P1-5 a
breach exposes provider PII.

**Remediation:** Hash the email at registration time
(`keccak256(lowercase(email))`) and store the hash. Only re-derive the
clear email for sending notifications, by recording the hash → cleartext
mapping in a separate write-only store (e.g. encrypted Postmark account).

## P3 — Defense in Depth (backlog)

### P3-1. Caret ranges on cryptographic deps

**File:** `package.json:36-41`, `packages/core/package.json:20-26`
**Confidence:** 10/10

`snarkjs ^0.7.6`, `poseidon-lite ^0.3.0`, `@zk-kit/lean-imt ^2.2.4`,
`@noble/curves ^1.9.0` — caret ranges allow patch+minor bumps. A behavior
change in any of these breaks the commitment/nullifier scheme for
existing deposits — funds become un-spendable.

**Remediation:** Pin exactly (`"snarkjs": "0.7.6"`) for the three
cryptographic deps. Bump deliberately, in a separate PR, with an end-to-end
test that proves a pre-bump deposit can still withdraw post-bump.

### P3-2. In-memory consumed-tx-hash set lost on Lambda restart

**File:** `src/lib/facilitator-authz.ts:56, 417-419`

If Upstash is absent (per P1-4) AND `ZBASE_FEE_REQUIRED=true`, a cold
start wipes `memConsumedTxHashes`. The same access-token tx hash can
re-authorize multiple nullifiers. Low severity because (a) Upstash should
always be set in prod and (b) `ZBASE_FEE_REQUIRED=false` today.

**Remediation:** Same as P1-4 — assert Upstash at boot.

### P3-3. `/api/x402-pay` leaks payment tx hash to third-party service

**File:** `src/app/api/x402-pay/route.ts:80-85`

```ts
const serviceRes = await fetch(url, {
  headers: {
    "X-Payment-Tx": withdrawData.txHash,
    "X-Payment-Method": "zbase-private",
  },
});
```

The `url` is user-controlled (any x402 endpoint). The route fetches it
with the withdraw tx hash in a header. The third-party endpoint learns
which specific on-chain tx paid them. Probably intended (so the
provider can verify payment) but the hash is also the link between the
buyer's deposit and this settle — a curious provider can subpoena the
log or sell the data to a chainalysis firm.

**Remediation:** Use a content-bound payment proof (e.g. signed nonce
the provider can verify against the on-chain event) instead of leaking
the tx hash directly.

### P3-4. `/api/demo/run` reads raw `x-forwarded-for` (no middleware)

**File:** `src/app/api/demo/run/route.ts:93-102`, `src/middleware.ts:91`

The middleware matcher includes `/api/facilitator/*`, `/api/withdraw`,
`/api/asp-update`, `/api/x402-pay` — NOT `/api/demo/run`. The demo
route reads `x-forwarded-for` for IP-based rate limiting. The code says
"never log it" but it's still observable in the function's runtime
memory (and any exception that captures `req` for Sentry would surface
it).

**Remediation:** Hash the IP before storing it in `ipLastRunAt`. Or
move the rate limit to Upstash with a hashed key.

### P3-5. Backup file in working tree

### P3-6. Error responses bubble raw `error.message` (200-500 chars)

**Pattern across:** `src/app/api/facilitator/authorize/route.ts:283`,
`src/app/api/facilitator/settle/route.ts:392`,
`src/app/api/withdraw/route.ts:636`

Catch blocks like `error: (error as Error).message?.slice(0, 500)` leak
stack frames, library internals, file paths in error messages. Not
exploitable directly but accelerates other attacks (lib version
fingerprinting, path disclosure for traversal probes).

**Remediation:** Return a stable error code + opaque request ID. Log
the full error server-side with the request ID.

### P3-7. `/api/skill` + `/api/prompt` echo `request.url` host into served content

**File:** `src/app/api/prompt/route.ts:15-16`

```ts
const url = new URL(request.url);
const baseUrl = `${url.protocol}//${url.host}`;
```

The host is interpolated into a markdown / prompt response. A
maliciously-set `Host: evil.com` header (Vercel passes through Host
header in many configs) would cause `baseUrl = https://evil.com`. If an
AI agent installs this prompt as instructions, it would POST sensitive
operations to evil.com.

**Remediation:** Use `process.env.NEXT_PUBLIC_APP_URL` instead of
`request.url`. Same fix that `demo/run` already does at line 617.

### P3-8. CI/CD is implicit (Vercel git-connection only) — no commit-signing

There is no `.github/workflows/` directory. Deploys happen on every
push to main via the Vercel GitHub app integration. There is no
required commit signature, no required PR review, no required CI gate.

**Remediation:** Add a minimal `.github/workflows/ci.yml` that runs
`npm test` + `forge test` on every PR. Add CODEOWNERS so PRs require
review from a known set. Optionally enforce signed commits via branch
protection.

### P3-9. Sensitive operational artifacts gitignored individually — easy to miss one

`.gitignore:121-126, 173-178, 187` lists many sensitive paths
individually (`docs/bd/`, `docs/ceremony/`, `docs/sales/exposure-audit/`,
`/decks/`, `/sales/`, `.env.local.backup-*`). A future contributor
adding a sibling directory will not be covered.

**Remediation:** Move all sensitive operational data into a single

### P3-10. Snarkjs trusted-setup keys directory + circuit WASM served from `public/`

**File:** `public/circuits/withdraw/{withdraw.wasm, groth16_pkey.zkey, groth16_vkey.json}`

The proving key (`groth16_pkey.zkey`) and WASM are served from `/public`
— public-readable static assets. Per CLAUDE.md these are the
`trusted-setup/final-keys/` versions that match the deployed verifier
(good). Worth confirming the keys' SHA256 matches the upstream 0xbow
release before any public flip — a swapped zkey breaks proof
verification (CLAUDE.md flags "ZKEY MISMATCH" as a known gotcha).

**Remediation:** Add a `npm run preflight:zkey-hash` check that
verifies the SHA256 of every file in `public/circuits/` against a
pinned manifest committed to the repo.
